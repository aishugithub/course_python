## What this project is

`course_python` is a React + Vite single-page app that delivers an interactive, self-paced Python course, publicly branded as **"Foothold"** (tagline: *"Have you got your foothold on Python yet?"*). It started as a closed course for B.Tech students at Sri Ramachandra Faculty of Engineering and Technology, and as of 2026-07-01 is being repositioned as a free course for **any novice programmer worldwide** — no account required to browse. It lives at `C:\aishu\courses\course_python`, is a git repo, and deploys to GitHub Pages at `https://aishugithub.github.io/course_python` via `npm run deploy` (which runs `vite build` then `gh-pages -d dist`). Login, self-registration, per-student progress, and usage analytics all go through a Google Apps Script backend (`Code.gs`, deployed separately from the frontend), configured in `config/gas.config.js` and called from `src/shell/api.js` / `src/shell/analytics.js`.

## Architecture — the things that matter

The whole app is built around one simple idea: lessons are fully independent, self-contained React components, and one config file decides which ones exist and in what order.

`config/course.config.js` is the only file you edit to change the course's structure. It exports `COURSE_CONFIG`, an object with `courseId`, `courseTitle`, `subtitle`, `batch`, and a `modules` array. Each module has a `moduleId`, `moduleTitle`, and a `units` array of `{ unitId, title }` pairs. `unitId` must exactly match a filename in `src/lessons/` (without the `.jsx` extension) — that's the only link between the config and the actual lesson code.

`src/lessons/UnitX_Y.jsx` — one file per lesson. Every lesson file is completely self-contained: its own local colour-palette constant, its own widgets, zero imports from other lesson files or from each other. This is deliberate — it means any single lesson can be rewritten, deleted, or handed to a different author without touching anything else. `src/shell/App.jsx` discovers every file in this folder automatically using Vite's `import.meta.glob('../lessons/*.jsx')`, so dropping a new `UnitX_Y.jsx` file in and adding a matching entry to `course.config.js` is the entire process for adding a lesson — no other file needs to change. **This session's shell changes (below) never touched a single lesson file — that boundary is intentional and should stay intact.**

`src/shell/App.jsx` is the app's router/state machine. It owns a `view` state (`'landing' | 'login' | 'dashboard' | 'lesson'`), the `student` object (`null` = browsing as a guest), `completedUnits`, and the currently active lesson. It dynamically imports whichever lesson file matches the unit clicked, and renders it with two props: `student` and `onUnitComplete` (a callback the lesson must call exactly once, when the learner finishes — this both persists progress and fires a `lesson_complete` analytics event).

`src/shell/Dashboard.jsx` renders every module and its units as clickable cards, reading straight from `COURSE_CONFIG`. Navigation is free — every unit is always clickable regardless of what's completed — `completedUnits` only controls the ✅/▶️ icon and the overall percentage bar. It's guest-aware: shows "Browsing as Guest" + a "sign in to save progress" prompt when `student` is `null`, or the student's name/roll number + a "Sign Off" button when signed in.

## The lesson template every unit follows

Every `UnitX_Y.jsx` file, without exception, has this shape: a header showing `MODULE X › UNIT X.Y` plus a live "N / total done" counter; a thin animated progress bar; a horizontal tab strip of 4-5 sections (the last one is always the quiz); a content card that renders whichever section is active; a "Mark Complete & Continue" button that advances to the next tab (hidden on the quiz tab, since the quiz has its own progression buttons); and a closing multiple-choice quiz with instant colour feedback (green for correct, red for the student's wrong pick) plus a one-line explanation after each answer, ending in a completion screen that shows a score, a contextual message, and previews the next unit or module. Only the quiz's `onComplete` callback calls `onUnitComplete` — that is the single point where a unit's completion is actually persisted.

Every file defines the exact same colour palette (dark, GitHub-inspired): background `#0D1117`, surface `#161B22`, card `#1C2333`, accent blue `#58A6FF`, solid-button blue `#1F6FEB`, success green `#3FB950`, warning yellow `#D29922`, purple `#BC8CFF` for "key insight" callouts, error red `#F85149`, plus orange/teal used for variety in some lessons. Copy this object verbatim into any new lesson file rather than inventing new colours.

## Teaching philosophy — how content gets designed, not just coded

Every widget teaches exactly one idea through interaction — clicking, dragging a slider, stepping through an animation, guessing before revealing — never through a wall of static text. Analogies come before jargon (a program is "a recipe," a variable is "a locker only you can open"). Each unit closes with a quiz that gives immediate feedback and an explanation, not just a score.

The one rule that most shaped Module 4, and should carry forward to every future unit that introduces a new core CS concept: **don't just show the syntax — motivate the need for it first, contrast it with a lower-level language (usually C) to show what Python is actually doing for you, and where relevant, visualise what's happening in memory or at the hardware level.** This came directly from feedback while building Unit 4.2 (Variables & Memory): before naming "variables," the lesson proves why one is needed at all (a football score-counter that literally cannot count without one), then shows an actual row of numbered memory slots being reserved and reused, and only then contrasts `score = 0` in Python against `int score = 0;` in C — framing dynamic typing as a genuine advantage rather than a syntax quirk. Apply this same need → lower-level contrast → memory/hardware visualisation sequence to future concepts: functions and the call stack, lists as contiguous memory, references/aliasing, recursion.

The whole course is explicitly built on **Vygotsky's Zone of Proximal Development and scaffolding theory** — this is now stated on the public Landing page (see below) and is genuinely how content should keep being designed: introduce a new concept only once the learner has exactly the prior pieces needed to understand it, provide just enough support (an analogy, a visualization, a guided interaction) to carry them across, then let that support fall away as the next concept builds on this one. If Aishu ever wants to write this course up as education research, this framing — and the "need → lower-level contrast → visualisation" sequence above — is the load-bearing pedagogical claim to build on.

Units are built and delivered one at a time, not batched — each finished `.jsx` file is copied into `src/lessons/` and shown to Aishu immediately, before starting the next unit. Keep doing this for future modules.

**Comment style:** Module 4's files (`Unit4_1.jsx`–`Unit4_4.jsx`) carry heavy, line-by-line explanatory comments — that was requested at the time to document the app's architecture while it was being established. Starting with Module 5, Aishu asked to stop that: the conventions are now well understood and no longer need re-explaining in every file. From `Unit5_1.jsx` onward, lesson files use only light section-divider comments (e.g. `// ── Widget Name ──`), matching the original pre-Module-4 style (see `Unit1_1.jsx`, `Unit2_4.jsx`, `Unit3_3.jsx`). Do not retroactively strip Module 4's comments; just don't add that density of comments to new files. **This same light-comment convention was used for all the shell files touched this session** (`App.jsx`, `Login.jsx`, `Dashboard.jsx`, `Landing.jsx`, `analytics.js`, `guestProgress.js`, `Code.gs`) — a short explanatory block only where something genuinely non-obvious is happening (e.g. why `handleRegister` reuses the Students sheet's columns positionally), not line-by-line.

## Shell/product work completed 2026-07-01 (separate from lesson content)

This was a distinct pass of work, prompted by Aishu wanting to open the course to the public. None of it touched `src/lessons/*.jsx`.

**Rebrand:** "SRET E-Learning" / "Sri Ramachandra Faculty of Engineering and Technology" branding removed from `Login.jsx` and `Dashboard.jsx`, replaced with **"Foothold"** and the tagline "Have you got your foothold on Python yet?"

**Guest-first access (new `src/shell/Landing.jsx`, rewired `App.jsx`):** The app now opens on a Landing page, not a login wall. Landing explains what the course is, who it's for, states the ZPD/scaffolding pedagogy in plain language, and offers two paths: "Explore the Dashboard" (goes straight in as a guest, `student = null`) or "Sign In / Register". Guests can browse and complete every lesson with zero friction; their progress is tracked client-side only, via `src/shell/guestProgress.js` (a small localStorage helper, key `foothold_guest_progress_v1`), not in Sheets. Signing in is purely optional and only buys you progress-sync across devices.

**Self-registration (`Code.gs`: new `register` action / `handleRegister`; `Login.jsx`: Sign In / Create Account toggle; `api.js`: `registerStudent()`):** Anyone can now create an account without Aishu manually adding a row to the Students sheet. The email address doubles as the username; the password is a new one invented just for this site (the registration form carries an explicit, visible warning that it is **not** the person's email account password — this was a specific, deliberate requirement from Aishu, worth preserving in any future redesign of that screen). Under the hood, `handleRegister` reuses the exact same five Students-sheet columns `handleLogin` already reads positionally (`[rollNo/username, password, name, batch, email]`) — a self-registered user's row just has their email in the "rollNo" slot and `"Self-registered"` in the "batch" slot. No sheet schema change was needed or made.

**Sign Off:** `Dashboard.jsx` now has a "Sign Off" button (only shown when signed in, not for guests) that clears `student`/`completedUnits` in `App.jsx` and returns to the Landing view.

**Mobile-friendly lesson navigation:** The original "← Dashboard" fix used a text pill button plus a 150px left-padding shift of the whole lesson — Aishu flagged this as wasting too much width on phone screens. **Current, correct version:** a small 36px circular icon-only button (just "←") fixed at the top-left corner, with `title`/`aria-label="Back to Dashboard"` for a hover tooltip on desktop, and zero layout shift — lessons render full-bleed on every screen size, exactly as before this whole nav investigation started. If this ever gets revisited, don't reintroduce a permanent margin/shift; the icon-only + tooltip approach was the agreed-on fix.

**Usage analytics (new `src/shell/analytics.js`; `Code.gs`: new `logEvent` action / `handleLogEvent`):** A minimal, deliberately small event set — `session_start` (once per app load, fired from a `useEffect` in `App.jsx`), `lesson_open` (in `handleSelectUnit`), `lesson_complete` (in `handleUnitComplete`), and `signup` (in `Login.jsx`'s `handleRegister`, only on a genuine new account, not every sign-in). Every event carries an anonymous ID (`foothold_anon_id` in localStorage, generated once via `crypto.randomUUID()`) that persists across guest browsing *and* after a later sign-up — this is what makes a real guest→signup conversion trace possible, not just a raw signup count. `handleLogEvent` auto-creates an `Events` tab in the spreadsheet on first call (columns: `Timestamp, AnonId, UserId, EventType, CourseId, UnitId`) — no manual sheet setup required. **Design rule that must be preserved in any future analytics work: `logEvent()` is fire-and-forget and never awaited by its callers — a slow or failed analytics call must never block or break the actual learning experience.** Verified live 2026-07-01: `session_start` and `lesson_open` are confirmed working end-to-end (real rows seen in the Events tab). `lesson_complete` has not yet been confirmed live — Aishu should finish one lesson's quiz and check the Events tab to close that loop. A Looker Studio dashboard on top of the Events tab was agreed on as the reporting layer but has **not been built yet** — the tab is just raw rows today.

**Important operational note — Code.gs must be manually redeployed:** Every `Code.gs` change this session (register, logEvent) requires Aishu to paste the updated code into the Apps Script editor (Extensions → Apps Script from the Sheet) and do Deploy → Manage deployments → edit → **New version** → Deploy. Editing the file alone, or anything on the frontend, does **not** push Apps Script changes live. If a new backend feature "isn't working," check this first before debugging code.

**Sandbox limitation, for whoever picks this up next:** this project's `node_modules` were installed on Windows; a Linux sandbox (if used again) cannot run `vite build`/`esbuild` against them (`Cannot find module @rollup/rollup-linux-x64-gnu`, `@esbuild/win32-x64` platform mismatch). All verification of shell changes this session was done by manually re-reading files, not by running a build. Aishu runs `npm run build` / `npm run dev` locally to actually confirm things compile.
